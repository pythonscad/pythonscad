# How PyQt6 is wired into PythonSCAD

This describes the current state of the PyQt6 integration: what it does for a
user, how the bindings are produced and packaged, how versions are chosen, and
where the rough edges are. It is a snapshot of the tree as of October 2026,
written so the design can be reworked with the facts in one place.

## What PyQt6 is for

PythonSCAD's own GUI is a Qt application. The PyQt6 work lets Python code
running inside that process reach the live Qt objects and build UI on top of
them. There are three distinct features, and they share one mechanism.

1. **Dialogs and menus.** A script or `.pythonscadrc` can open a Qt dialog
   parented to the running main window, or add an entry to the menu bar.
2. **Editor-triggered forms.** A Python class can declare a calltip and a
   callback. Typing `myclass(` in the editor then shows a clickable calltip,
   and clicking it runs the callback, which typically opens a dialog and
   rewrites the call's arguments in the source.
3. **Custom Customizer widgets.** A Python function can register a widget
   factory, and `add_parameter(..., type="that_name")` then renders that
   widget in the Customizer sidebar, persisting its value with the parameter
   sets.

All three need the same two things: a `PyQt6` that was compiled against the
exact Qt libraries the PythonSCAD binary was linked with, and a way to turn a
raw C++ object pointer into a Python Qt object and back.

## Why the bindings have to be built at all

PyQt6 is not a pure-Python package. Its modules (`QtCore`, `QtWidgets`, …)
are extension modules generated by SIP from Qt's C++ headers and compiled
against a specific Qt and a specific Python ABI. A wheel from PyPI is built
against the Qt that Riverbank packages, which is not the Qt that PythonSCAD
links. Loading it inside PythonSCAD would mix two copies of the Qt libraries
in one process.

So the bindings have to be compiled against the same Qt the application uses.
That compile takes a while and needs the full Qt development stack, which is
why the result is cached and reused instead of being rebuilt on every
package.

## Where each package gets PyQt6

No packaging job downloads a `pyqt6-bindings-v1-*` GitHub release anymore.
Those releases were an immutable cache for bindings compiled ahead of time.
The workflows that consumed them now obtain PyQt6 as follows.

### Debian and RPM

Qt6 packages depend on the distro's `python3-pyqt6` (`debian/control`,
`pythonscad.spec`). The packaging jobs do not compile PyQt6. The embedded
interpreter finds that package because `config.executable` is set only when
a real `python` binary sits next to the application
(`src/python/pyopenscad.cc`). A local build directory has no such binary, so
CPython uses the interpreter it was linked against, including
`/usr/lib/python3/dist-packages`.

Ubuntu 22.04 stays on Qt5 and the dependency is stripped while the package
is built (`scripts/build-debian-package.sh`). Rocky Linux 9's repositories
do not ship `python3-pyqt6`, so the RPM spec adds that dependency only on
Fedora. Both packages run without PyQt.

### AppImage

The Qt6 AppImage job installs `python3-pyqt6` on the Ubuntu runner.
`scripts/create_appimage.sh` copies that package onto the `PYTHONPATH` the
image already exports and copies any shared libraries the extension modules
need. Python loads PyQt6 with `import`, so linuxdeploy would not see it on
its own. The image does not use the end user's PyQt6.

### Windows

The release workflow (`.github/workflows/build-windows-native.yml`) still
compiles PyQt6, and only that workflow does. `actions/cache` stores the
built tree, keyed by the Qt version, the Python version, and the hashes of
`scripts/ci/pyqt6-versions.json` and
`scripts/ci/pyqt6-build-requirements.txt`. A cache miss rebuilds. GitHub
drops an unused cache entry after 7 days, so the first build of a later
release compiles again. The SIP build keeps PyQt's complete module and
platform feature probes enabled so unsupported Windows features are excluded
correctly.

The link uses an import library generated with `gendef` and `dlltool` from
the embeddable `python3XY.dll` (`scripts/libpython_patch.sh`), which is the
DLL the installer ships. MSYS2's import library names `libpython3.X.dll`
and is not rewritten in place anymore.

### macOS

`scripts/ci/prepare-macos-pyqt6-qt.sh` downloads the macOS PyQt6 wheel and
the matching `PyQt6-Qt6` wheel. The wheel's frameworks are runtime-only, so
the script installs the official Qt SDK of that exact version for headers,
`moc` and `macdeployqt`, then replaces the SDK's framework binaries and
plugins with the wheel's. QScintilla is built from source against that
prefix. Homebrew still supplies CGAL, Boost, OpenCSG and the other non-Qt
libraries. The bindings themselves come from the wheel and are copied to
`libraries/python/PyQt6`. The wheel is `abi3`, so the CPython bundled in
the `.app` has to be 3.11 or newer, which the Homebrew Python already is.

## How versions are chosen

On Linux the distro chooses both Qt and PyQt6, and they match because they
were built together. Windows still resolves a PyQt sdist from the Qt minor
via `scripts/ci/pyqt6-versions.json`. macOS takes the newest PyQt version
listed in that file and then the Qt frameworks that wheel depends on.

`scripts/ci/pyqt6-versions.json` maps a Qt minor to a reviewed PyQt release:

```json
"6.10": "6.10.2",
"6.11": "6.11.0"
```

`scripts/ci/resolve_pyqt6_version.py` looks up the exact minor and exits with
an error if it is absent. There is no fallback. It then fetches the sdist URL
for that version from `https://pypi.org/pypi/PyQt6/json` at build time.

The code-generation toolchain is pinned outright in
`scripts/ci/pyqt6-build-requirements.txt`:

```text
sip==6.17.1
PyQt-builder==1.19.1
PyQt6-sip==13.13.0
packaging==26.3
```

`scripts/ci/pyqt6-build-requirements-py3.9.txt` carries older pins for the
distributions whose Python is too old for those (currently PyQt6-sip
13.10.2).

## What actually gets compiled

Only the Windows release compiles PyQt6. Debian, RPM, the AppImage and
macOS do not.

1. Detect the Qt version from `qmake6`.
2. Resolve the PyQt version and download the sdist from PyPI.
3. Rewrite the SIP files to drop free comparison operators
   (`scripts/ci/patch_pyqt6_free_operators.py`) and patch pyqtbuild's Python
   library lookup (`scripts/ci/patch_pyqtbuild_win32_pythonlib.py`).
4. Run `sip-build` with its full feature probes, then `make` and `make install`.
5. Copy the resulting `PyQt6` package out, and add the `PyQt6-sip` extension
   module installed separately from the pinned requirement.
6. Verify with `objdump` that `QtCore` links against `python3XY.dll`.

## How a packaged build finds PyQt6 at runtime

`CMakeLists.txt` installs the whole `libraries/` tree into the resource
directory. The embedded interpreter adds
`<resource path>/libraries/python` to `sys.path`
(`src/python/pymod.cc`, `pythonOverlayLibraryPath()`), and the AppImage
launcher exports the same directory on `PYTHONPATH`
(`scripts/create_appimage.sh`). So `import PyQt6` resolves to the bundled
copy with no extra configuration.

Nothing in the codebase builds or references PyQt5. A script that imports
`pyscadforms` on a Qt5 build gets a plain `ImportError` saying the feature
needs a Qt6 package. The Ubuntu 22.04 package is that Qt5 build.

The Windows job additionally checks the packaged result: it runs the built
`pythonscad.com --repl` with `from PyQt6 import ...` and
`sip.wrapinstance(qapp_ptr(), ...)` and greps for a marker. The AppImage
smoke test (`scripts/release-smoke/common-smoke.sh`) does the same for Qt6
packages only.

## What a local build or a distro package does

A build from source on Linux contains no bundled PyQt6. `import PyQt6`
resolves to the distro package, which matches the Qt the binary links when
both come from the same distribution. Install `python3-pyqt6` for that.
The Debian and Fedora packages depend on it. Ubuntu 22.04 and Rocky Linux 9
do not, because their repositories do not ship it.

## How Python reaches the running application

Qt allows one `QApplication` per process, and PythonSCAD already created it.
`src/python/py_io.cc` exposes two functions that return the raw pointer as a
Python integer:

- `qapp_ptr()` returns `qapp_global`.
- `mainwindow_ptr()` returns `mainwindow_global`, which `MainWindow::customSetup()`
  sets while loading `.pythonscadrc`.

Python turns that integer back into a real Qt object with SIP:

```python
from PyQt6 import sip, QtWidgets
mw = sip.wrapinstance(mainwindow_ptr(), QtWidgets.QMainWindow)
```

`sip.wrapinstance` does not copy anything. It wraps the existing C++ object,
so the resulting `mw` is the actual main window and can parent dialogs.

The custom-widget path runs the conversion in the other direction.
`src/python/pywidget_bridge.cc` calls the registered factory, then uses
`PyQt6.sip.unwrapinstance` to recover the `QWidget*` from the Python object
so the Customizer can embed it. It falls back to a top-level `sip` module for
older builds.

## The editor form protocol

`src/gui/PythonApi.cc` (`PythonApi::callTips`) and the equivalent in
`src/gui/ScadApi.cc` run whenever the editor wants a calltip. They call
`python_get_static_calltip()` (`src/python/pyopenscad.cc`), which looks up
the name in the Python main module and calls its `get_calltip()` if it has
one. When that succeeds, the calltip is marked with
`lastCallTipIsPythonForm` and a clickable arrow glyph is appended.

Clicking the calltip fires `SCN_CALLTIPCLICK`. `ScintillaEditor::onCallTipClicked`
(`src/gui/ScintillaEditor.cc`) checks the flag and, on the next event-loop
turn, calls `python_call_static_editor_method(name, "on_editor_trigger", pos)`.
`pos` is the character offset just after the call's opening parenthesis,
found by scanning backwards for the matching bracket.

The callback reads and rewrites the call through two more functions in
`py_io.cc`: `editor_get_call_args(pos)` returns the text between the
parentheses, and `editor_replace_call_args(pos, text)` replaces it.

`libraries/python/pyscadforms.py` builds on this. `parse_arguments(cls, text)`
parses the existing argument text against `cls.__new__`'s signature so a form
can pre-fill its fields and round-trip arguments it does not understand. The
module also ships two complete implementations: a `polygon` class with a
drawing canvas and a `cube` class with a size form and a preview. Both
capture the original builtin before redefining the name, and both return the
real geometry from `__new__`, so a call still produces ordinary geometry when
the form is never opened.

## The Customizer widget protocol

`add_parameter_widget(typename, factory)` (`py_io.cc`) stores the factory in
`customizer_widget_factories`. When the Customizer builds its panel,
`pywidget_create()` calls `factory(name, default)`, unwraps the returned
object to a `QWidget*`, and `src/gui/parameter/ParameterPyQtWidget.cc` hosts
it. The widget must provide `get_value()`, `set_value(value)` and a
`valueChanged` signal. Values cross the boundary as JSON.

`set_modal_dialog_active(flag)` guards a deadlock: background geometry
evaluation takes and releases the GIL from worker threads, while a modal Qt
dialog runs a nested event loop with its own GIL handling. The flag tells the
evaluation side to stay out while the dialog is open.

## `.pythonscadrc`

`MainWindow::customSetup()` (`src/gui/MainWindow.cc`) runs once at startup.
It reads `.pythonscadrc` from `PlatformUtils::pythonUserConfigPath()`. On
Linux that is `~/.config/PythonSCAD/` (`$XDG_CONFIG_HOME/PythonSCAD`). There
is no fallback to `~/.config/OpenSCAD`. It executes the file in the shared
Python namespace, then
calls `setup()`. Menu registration belongs in `setup()` because the menus
exist by then. Names defined during this load are recorded by
`snapshotPythonInventory()` and survive the per-render namespace reset, which
is why editor-form classes have to live here rather than in a model script.
Definitions made only inside a script disappear the next time a different
document is rendered.

## Qt5

`-DUSE_QT6=OFF` and the Qt5 dependency profile stay in the tree. The only
published Qt5 artifact is the Ubuntu 22.04 package, which has no PyQt. The
Qt5 AppImage is gone. There is no PyQt5 build.

## Supply chain

What is pinned:

- The SIP toolchain, by exact version, in the requirements file. `pip
  install` checks the wheel hashes pip records for those versions.
- The PyQt sdist, indirectly: the version is reviewed and committed in
  `pyqt6-versions.json`, and the sdist URL is taken from PyPI's JSON API for
  that exact version.

What is not pinned:

- The sdist is downloaded over HTTPS with `curl -L -o` and extracted with no
  checksum or signature check. A compromise of that PyPI release, or of the
  connection, would flow into the published bindings unnoticed.
- `PyQt6-sip` is installed from PyPI by version pin only, again without a
  hash.
- The Qt itself comes from the distribution, the PyQt6 wheel, or MSYS2,
  with no checksum recorded here.
- The macOS wheels are downloaded from PyPI by version pin, without a hash.

## Where this design hurts

- **Windows still compiles PyQt6.** The release cache absorbs repeats inside
  a 7-day window. The first build after that, or after a Qt or Python bump,
  pays the compile again.
- **The macOS wheel has no SDK.** Headers and `macdeployqt` come from the
  official Qt build of the same version, and only the framework binaries and
  plugins are swapped for the wheel's. A Riverbank rebuild that is not
  interchangeable with the official build of that version would break the
  link.
- **Old `pyqt6-bindings-v1-*` releases are still on GitHub.** Nothing in the
  tree publishes or downloads them. Delete them once a release build of the
  AppImage, the macOS app and the Windows installer has succeeded without
  them.

| Path | Role |
|---|---|
| `.github/workflows/build-appimage.yml` | Installs `python3-pyqt6` and copies it into the image |
| `.github/workflows/build-macos-release.yml` | Links the Qt inside the PyQt6 wheel and code-signs the bindings |
| `.github/workflows/build-windows-native.yml` | Compiles PyQt6 on a cache miss and smoke-tests the package |
| `.github/workflows/build-debian-packages.yml` | Depends on distro `python3-pyqt6`; Jammy stays Qt5 |
| `.github/workflows/build-rpm-packages.yml` | Depends on distro `python3-pyqt6` on Fedora |
| `scripts/ci/prepare-macos-pyqt6-qt.sh` | Wheel Qt, QScintilla, and the PyQt6 package for macOS |
| `scripts/ci/build-pyqt6-bindings-windows.sh` | Windows SIP build of the modules the app uses |
| `scripts/libpython_patch.sh` | `gendef` + `dlltool` import library for `python3XY.dll` |
| `scripts/ci/resolve_pyqt6_version.py` | Qt minor to PyQt version, then PyPI sdist URL |
| `scripts/ci/pyqt6-versions.json` | The reviewed version map |
| `scripts/ci/pyqt6-build-requirements.txt` | Pinned SIP toolchain |
| `scripts/ci/pyqt6_smoke_test.py` | Import and `QApplication` check |
| `libraries/python/pyscadforms.py` | Argument parser plus the `polygon` and `cube` forms |
| `src/python/py_io.cc` | `qapp_ptr`, `mainwindow_ptr`, editor helpers, widget registration |
| `src/python/pywidget_bridge.cc` | Factory call and SIP unwrap for Customizer widgets |
| `src/python/pyopenscad.cc` | `get_calltip` lookup and `on_editor_trigger` dispatch |

| `src/gui/ScintillaEditor.cc` | Calltip click handling |
| `src/gui/parameter/ParameterPyQtWidget.cc` | Hosts a Python widget in the Customizer |
| `src/gui/MainWindow.cc` | Loads `.pythonscadrc` and calls `setup()` |
